# Feeds

A feed is one configured source of observations: a built-in poller such as OpenSky, a JSON API, a byte stream from a receiver or a TAK server, or an external system that sends to Sentinel over TCP or UDP. This page covers the lifecycle of a feed, the management API, configuration and secrets, what each driver does, how several ingest replicas share the work, and what to write to add a driver.

## Lifecycle

```
operator / gateway ──▶ feeds (desired state, Postgres) ──LISTEN/NOTIFY──▶ every ingest replica
                                                                              │ lease: one owner per feed (feed_leases)
                                                                              ▼
                                   driver ──▶ runner (provenance, dedupe, raw bounds) ──▶ observations.raw (protobuf)
                                                                              ▼
                       entity-service: resolve identities ──▶ fuse (newest fix wins) ──▶ entities, observations, entity_sources
                                                                              ▼
                                                     entities.events ──▶ track, alert, search, analytics, gateway WebSocket
```

1. **Desired state** lives in `sentinel.feeds`: id (an immutable slug), name, driver, `config` (validated against the driver's JSON Schema plus the common options), `secret_refs`, `enabled`, `version`. Every write bumps `version` and notifies the replicas.
2. **Ownership.** With leases enabled (the default) each enabled feed runs on exactly one replica. Replicas heartbeat `ingest_replicas`; a feed's preferred owner is chosen by rendezvous hashing over the live replicas that may run it (a connection that binds a port among the listener replicas, every other feed among the ordinary replicas; see Listeners below), or by `config.pinnedReplica`; the owner holds a `feed_leases` row it renews every `LEASE_TICK_SEC` (2 s) with a `LEASE_TTL_SEC` (15 s) expiry. Acquisition bumps the fencing token, which travels on every observation (`x-fence` header, `fencing_token` field) and guards status writes, so a replica that lost its lease cannot overwrite the new owner's work. A non-preferred replica steps in only after the preferred one had a TTL to claim a free feed, and hands the feed back after `LEASE_REBALANCE_SEC` (30 s) once the preferred replica is live.
3. **Running.** The supervisor builds the driver, wraps it in a runner and starts it. A driver that fails to start or exits with an error is restarted with backoff (`FEED_RETRY_MIN_SEC` to `FEED_RETRY_MAX_SEC`). A version bump restarts the feed with the new configuration.
4. **Observations.** The runner stamps provenance (feed id, driver, receive time, lease token), drops any `EMPLACEMENT` identity the service did not set (only the emplacements feed reports as an emplacement), guarantees an identity (a canonical one such as ICAO24 or MMSI when the decoder found one, else `FEED_LOCAL` over feed id and source entity id), bounds the raw payload (`rawPayload: none|bounded|full`, bounded to `RAW_PAYLOAD_MAX_BYTES`), suppresses a fix that repeats the previous one within a second and ten metres (still forwarding one every 5 s so downstream last-seen times move; a driver whose definition sets `NoRepeatSuppression`, such as `emplacement`, is exempt), computes the deterministic observation id, and publishes to `observations.raw` keyed by identity so one object's reports stay in order. Payloads nothing could decode go to `observations.dlq` (at most `DLQ_RATE_PER_SEC` per feed) with the reason and error in headers.
5. **Status.** The owner writes `feed_status` every 5 s: state (`starting`, `running`, `idle`, `degraded`, `error`, `stopped`), health from the time since the last report against `staleWarnSec` / `staleCriticalSec`, counters, last error, applied version and driver detail (area, credits, connections, lease token). `GET /feeds` from any replica overlays the live status for feeds running there and renders a row whose replica stopped reporting as `unassigned`.
6. **Outbound.** A connection (direction `out` or `both`) also runs a pump beside its driver on the owning replica: its own Kafka consumer group `sentinel-conn-<id>` on `entities.events` (and `alerts.events` unless `policy.alerts.enabled` is false), so offsets survive restarts and handovers and a slow remote never stalls another connection. Each event is checked against `config.policy` (loop and re-export guards first, then classification ceiling, entity type, feed, boxes), coalesced per entity (only the newest snapshot waits; a removal replaces any pending snapshot and is never dropped), spaced by `outbound.perEntityMinSec`, rate-limited by `outbound.maxEventsPerSec`, and handed to the driver. `deleted` and `aged_out` events become removals for entities the remote knows; an entity that stops passing the policy is removed after `outbound.policyExitGraceSec`; events older than `outbound.maxLagSec` are dropped rather than replayed. While the driver reports it is not connected the pump pauses and keeps the queue. `feed_status.detail.outbound` carries `delivered`, `deliveryErrors`, `denied`, `coalesced`, `dropped`, `queueDepth`, `tracked` and `consumerGroup`; `messagesTotal` and `lastSuccessAt` include deliveries. Losing the lease cancels the pump, which leaves the group so the new owner resumes from the committed offset.
6. **Fusion** happens in the entity-service: observations from different feeds that share a canonical identity update one entity, the newest source timestamp wins, rejected fixes are kept as observations with a reject reason, and per-feed ageout thresholds apply. See `docs/data-model.md`.

## Management API

Served by the ingest service on `HTTP_ADDR` (`:4000`) and proxied by the gateway under `/api/v1`. The gateway presents `X-Sentinel-Service-Token` (`INGEST_SERVICE_TOKEN`); reads need any authenticated user, writes need `sentinel-operator` or `sentinel-admin`, and so does reading dead letters. The gateway itself may push areas with the bare service token.

| Method | Path | Description |
|--------|------|-------------|
| GET | `/feeds?driver=&enabled=&capability=&direction=` | Every feed with its status (array); `direction=in` or `out` also matches `both`, `direction=both` only `both` |
| POST | `/feeds` | Create: `{ id?, name, description?, driver, config, secretRefs?, enabled? }`; the id is slugified from the name when omitted. 422 with `details[{path,message}]` on validation failure (a missing setting is reported at its own field, such as `/config/port` with `is required`, and a problem with the config as a whole at `/config`; the port and allowlist checks run once the rest passes, so fixing one 422 can reveal another), 409 on a duplicate id. The id `ports` is reserved |
| GET | `/feeds/{id}` | One feed |
| PUT | `/feeds/{id}` | Replace the mutable fields (`name`, `description`, `config`, `secretRefs`, `enabled`) |
| PATCH | `/feeds/{id}` | Merge patch; `config` merges one level deep, `null` removes a key; `id`, `driver`, `builtin` are immutable |
| DELETE | `/feeds/{id}` | 403 for a built-in feed (disable it instead). A feed that already has the id `ports` can only be deleted: `GET /feeds/ports` is the next row |
| POST | `/feeds/{id}/enable`, `/feeds/{id}/disable` | Persisted desired state |
| GET | `/feeds/{id}/status` | The status row (live when the feed runs on the answering replica) |
| GET | `/feeds/ports` | Help for choosing a listening port: `{ min, max, reserved[{from,to}], taken[{protocol,port,feedId,feedName,enabled}], suggested{tcp,udp} }` (a protocol with no free port has no entry). The Connections form reads it for its port hints. The answer is advice: a save checks again, and a port another process holds on the listener host shows only when the connection starts |
| GET | `/feeds/{id}/deadletters?limit=&payload=` | A connection's newest dead letters, newest first: `{ letters[{at,reason,error,driver,decoder,sender,size,payloadTruncated,partition,offset}], scanned, partial }`; `limit` is a positive integer (400 otherwise), clamped to 100 (default 20), and `payload=true` adds `payload` (the first 1 KiB, as text, or base64 when it is not UTF-8) and `payloadEncoding`. Needs `sentinel-operator` or `sentinel-admin` and a clearance at or above the feed's classification (403), since a dead letter is undecoded and the classification is the only bound on what it holds. 501 when `DLQ_PEEK_MAX_SCAN=0`, 502 when the topic cannot be read, 404 for an unknown feed. See Replicas and operations |
| GET, PUT | `/feeds/{id}/area` | Area of interest for drivers with the `area` capability: `{ active, clients, boxes[{north,south,east,west}] }`, at most four boxes that never cross the antimeridian; the response adds `live`, `idle`, `areaSqDeg`, `effectiveIntervalSec`, `creditsRemaining`, `lowCredits`, `lastPollAt`, `nextPollInSec`, `expiresAt`. 409 for a driver without the capability |
| GET, POST | `/feeds/{id}/tokens` | A `grpc` connection's ingest tokens. GET lists them (array of `{ id, feedId, name, prefix, classification, createdBy, createdAt, lastUsedAt, expiresAt, revokedAt }`); the list never carries a secret, only `prefix` (`si_` and the first eight characters). POST creates one from `{ name, classification?, expiresAt? }` and returns 201 with the same fields plus `token`, the `si_` secret, which appears in this response only and cannot be fetched again (only its SHA-256 is stored). `classification` is the token's ceiling: it defaults to the connection's classification (UNCLASSIFIED when it has none) and must be at or above the connection's and at or below your clearance, else 422 at `/classification`; `expiresAt`, when given, must be in the future (422 at `/expiresAt`); `name` is required (422 at `/name`). Both need `sentinel-operator` or `sentinel-admin` and a clearance at or above the connection's classification (403). POST on a connection whose driver is not `grpc` is 422 at `/driver`; 404 for an unknown feed; 501 when tokens are not enabled |
| DELETE | `/feeds/{id}/tokens/{tokenId}` | Revokes an ingest token: sets `revokedAt`, and a sender holding it stops authenticating. Idempotent, so revoking a revoked token is 204 again; 404 for an unknown token or one of another connection. Same roles and clearance as the rows above |
| GET | `/drivers`, `/drivers/{id}` | The catalog: id, name, description, source, `direction`, capabilities, `configSchema`, `secretFields` |

The feed resource carries `source` (the EntitySource label its observations use), `direction` (`in`, `out` or `both`: the driver's direction, narrowed by `config.direction` when set), `capabilities` (`poll`, `area`, `listen`), `builtin`, `version` and `status`. A feed that sends (`out` or `both`) is a *connection*: it consumes `entities.events` and `alerts.events` under the same lease and status machinery and pushes what its `config.policy` allows to the remote system.

## Configuration and secrets

`config` is validated against the driver's schema (served on `/drivers/{id}`) and the common options every driver accepts:

| Key | Purpose |
|-----|---------|
| `staleWarnSec`, `staleCriticalSec` | Health thresholds (defaults `FEED_STALE_WARN_SEC` 120, `FEED_STALE_CRITICAL_SEC` 300) |
| `backpressure` | `block`, `drop` or `nack` between a transport and its decoder; the transport default applies when absent |
| `pinnedReplica` | Run only on this replica. Optional: without it a connection that binds a port runs on a listener replica and every other feed on an ordinary one; with it the feed runs on the named replica whatever its role, so pinning is how an ordinary feed runs on a dedicated listener (see Listeners) |
| `classification` | Default level (`UNCLASSIFIED`, `CONFIDENTIAL`, `SECRET`, `TOP_SECRET`) stamped on every observation; a decoder may only raise it. Entities keep the highest level any feed reported. Link 16 feeds should set `SECRET`, since the decoder does not read the header's security field |
| `rawPayload` | `none`, `bounded` (default) or `full` raw bytes kept on each observation |
| `direction` | `in`, `out` or `both`; narrows a driver that can do both, never widens one (422 otherwise) |
| `policy` | Sharing policy of an `out` or `both` connection (422 on a driver that only receives): `entityTypes[]`, `feeds[]` (feed ids that must have contributed), `boxes[{north,south,east,west}]` (up to 16; `west > east` wraps the antimeridian), `classificationCeiling` (default `UNCLASSIFIED`), `reexport` (send entities another connection contributed to; a loop back to the same connection is always prevented), `alerts{enabled, minSeverity, types[]}`. Empty lists mean no restriction |
| `outbound` | Sink tuning: `queueMax` (10000), `perEntityMinSec` (5), `maxEventsPerSec` (200), `maxLagSec` (300), `policyExitGraceSec` (30) |

A config object with two keys that differ only in case (`transport` and `Transport`) is refused with 422, because the driver reads keys without regard to case and could pick either. The `body` of an `httpjson` request is exempt, and its `headers` are refused only for names that differ in case, as HTTP header names do.

Secrets never appear in `config`. Each driver declares `secretFields`, and `secretRefs` maps them to references the owning replica resolves at start: `env:VARIABLE_NAME` (the variable must be set on every replica) or `file:/absolute/path` (the file's contents, trimmed; how mounted secrets and PEM certificates arrive). Plain values are rejected. A secret a driver needs under the config is required: a TLS `tcp` listener without `tlsCert` and `tlsKey`, or with `tls.requireClientCert` and no `clientCa`, is a 422 at `/secretRefs/<key>` (`is required`) when it is saved, where it used to be created and then fail to start. The server reads this from the driver schema's `x-secrets.<name>.requiredWhen`, the way the form does: each key is a path from the config root (`tls/enabled`), a value or a list of values, a missing value counts as the schema's default, and every condition must hold. A driver whose schema states none (`stream`, which can read its TLS files from `certFile` and `keyFile`) is not asked for any. Mounted files appear under `/etc/sentinel/secrets` on the ingest and listener replicas alike: Compose mounts its gitignored `./secrets/ingest` folder there, and the Helm chart a Secret named by `ingestService.secretFiles.existingSecret` (the TAK certificates have their own mount at `/etc/sentinel/tak`). Variables for `env:` references come from `./secrets/ingest.env` under Compose (an optional `env_file` of both ingest services, one `SENTINEL_SECRET_NAME=value` line per variable, since Compose adds no prefix and the name must pass `INGEST_SECRET_ENV_ALLOW`; gitignored; Compose 2.24 or later) and from `ingestService.secretEnv.existingSecret` under Helm. Name them `SENTINEL_SECRET_<NAME>`, as the policy below asks.

**Secret policy.** A reference may name only what the deployment allows, because a driver sends its secrets to hosts the operator chooses. `INGEST_SECRET_ENV_ALLOW` lists the variables a reference may name, as exact names or prefixes ending in `*` (default `OPENSKY_*,AISSTREAM_*,SENTINEL_SECRET_*`: the built-in feeds and your own `SENTINEL_SECRET_` ones; a lone `*` allows any name). `INGEST_SECRET_FILE_DIRS` lists the absolute folders a `file:` reference may read (default `/etc/sentinel`, which holds the TAK and listener mounts); the stream driver's `tls` file paths (`caFile`, `certFile`, `keyFile`, `clientCaFile`) must be inside them too. **This is a breaking change**: earlier versions accepted any variable and any file. `INGEST_SECRET_ENV_ALLOW=*` restores the old behaviour for variables, and `INGEST_SECRET_FILE_DIRS=/` lifts the folder limit for files (links must still be relative, see below). A refused reference is a 422 at `/secretRefs/<key>` naming the variable or file and the setting that decides. A PATCH checks the feed's existing references again, so a policy narrower than the built-in `opensky` and `aisstream` references locks those feeds until it is widened. A stored feed that no longer passes fails to start with the same text as its last error, and `POST /feeds/{id}/disable` still works on it. Paths are cleaned and links followed: a link that leaves the allowed folders is refused, and a link inside one must be relative and stay inside it (Kubernetes' `..data` layout does). Files are read through this check every time they are read, so a Secret that Kubernetes updates in place is followed. Set the policy the same on every ingest replica, listener included (under Helm `ingestService.env` reaches both Deployments; Compose passes neither variable on, so add them to the `environment` of both services). Variables set through `secretEnv` or `env_file` can set any configuration the chart or Compose file leaves unset, such as `LEASE_ENABLED`, so put only secret material in them.

**Built-in feeds.** Five feeds are created at start: `opensky`, `celestrak`, `intelsky`, `aisstream` and `emplacements` (enabled by default, since it needs no credentials). `emplacements` is internal: its driver cannot back a connection, `POST /feeds` with `driver: emplacement` answers 422, and like any built-in feed it cannot be deleted. See `docs/emplacements.md`.

**CelesTrak notes.** CelesTrak has no API keys or accounts; it has a [usage policy](https://celestrak.org/usage-policy.php) instead. Elements update every two hours, the large groups (`active`, `starlink`) allow one download per update per IP and answer a repeat with 403, and more than 50 error responses in two hours from one IP lead to a firewall block. The driver fetches each selection once per refresh with a conditional request (`If-None-Match` / `If-Modified-Since`, so an unchanged file is a 304), honours `Retry-After`, and never refreshes more often than every two hours. On any other error it retries with backoff from 1 s to 60 s, which means a block is retried every minute: watch `status.detail.errors` and `lastStatus` on the feed, and keep selections few (each catalog number is one request). Six-digit catalog numbers (in use since July 2026) are carried in the OMM record; the synthetic two-line elements on each observation use a placeholder in the line's five-column field and the real id beside them. The map propagates satellites between fixes from those elements and draws the selected satellite's orbit (`docs/frontend.md`).

**IntelSky notes.** IntelSky needs no key or account; it throttles per IP (60 requests a minute on the live feed, 200 on `stats/*.php`) and answers 429 past that, without JSON error bodies, and asks commercial or high-volume users to contact it first. The feed has no area filter, so the driver polls the whole of it (about 75 aircraft) six times a minute; failures back off from 1 s to 60 s or honour `Retry-After`, never faster than the interval, and a body that is not JSON (IntelSky serves `text/html` even for JSON) is dead-lettered. `now` is in milliseconds and `dbFlags` is the operator's flag emoji, read as `countryOfOrigin` (`US`, `FR`, …). Aircraft are drawn in the military orange; the gateway's `/api/v1/aircraft/{hex}/path` serves their past paths from IntelSky's track endpoints (`docs/api-gateway.md`). IntelSky replaced adsb.lol: `ADSB_LOL` remains a valid source for old entities and track points, and existing databases drop the old feed with `DELETE FROM sentinel.feeds WHERE id = 'adsb-lol'; DELETE FROM sentinel.feed_ageout_config WHERE "feedId" = 'adsb-lol';`.

**aisstream.io notes.** aisstream.io needs a free account and an API key, and forbids using it from a browser, so only the ingest replica that owns the feed sees it. A connection must subscribe within 3 s of opening and may change its subscription at most once a second. The driver sends the whole subscription on connect, resubscribes only when the boxes change after rounding outward to 0.1° and at most every 2 s, waits 5 s for the `SubscriptionConfirmation` (else it reconnects), pings every 30 s, and reconnects with jittered backoff from 1 s to 60 s; the last failure stays in `detail.connections.<area|watchlist>.lastError` until a subscription is confirmed again. An account may hold three connections and this feed uses up to two, so a second deployment on the same key would hit the limit. The service drops consumers that fall behind and replays nothing: the driver reads into a 10 000-message buffer and counts what it cannot queue (`detail.dropped`) rather than block. It offers permessage-deflate, worthwhile since aisstream.io limits the bandwidth of uncompressed connections (`detail.connections.*.compression`). Messages are go-ais packets as JSON and go through the same mapping as the `nmea-ais` decoder, so vessels from aisstream.io and from a local receiver fuse on MMSI. Volume is modest: about 115 messages a second for the whole world and a few a second for the English Channel (October 2026). While a view is over the cap the map shows counts for aisstream.io vessels only; vessels known only from a receiver are hidden until the view is zoomed in below it.

**TCP and UDP connections.** These drivers are for systems that send to Sentinel instead of being polled. Each datagram of a `udp` connection is one message (JSON, NMEA and SBS may put several lines in one); a `tcp` stream is split by a framing. `format` picks the decoder, `sentinel` by default: the `sentinel.v1.Observation` message (`proto/sentinel/v1/observation.proto`; the Connections page offers the `.proto` files for download). With `encoding: protobuf` a TCP sender writes length-delimited messages (a varint length, then the message: Java `writeDelimitedTo`, Go `protodelim`) and a UDP sender one message per datagram; with `encoding: json` both send the protobuf JSON form, one message per line, and a line may instead hold a JSON array of up to 100 observations (on one line, since the line is the frame). An array is accepted or refused whole, an error names the failing element counted from 0 (`element 3: ...`), a 101st element is refused as `batch_too_large`, and each observation keeps its own element as its raw payload. The framing a format implies is `delimited` for `sentinel` protobuf, `line` for `sentinel` JSON, `xmlevent` for `cot`, `beast` for `beast` and `line` for the rest (set `framing: lengthprefix` for `link16` over TCP); `framing` overrides it. A message needs `source_entity_id` or an identity, and a position it carries must lie inside WGS84 bounds, else it is dead-lettered as `missing_identity` or `bad_position`. A message without `source_entity_id` takes `TYPE:value` of its first identity (`IMO:9321483`) as its source id, so identity-only senders keep their objects apart. A NaN or infinite number elsewhere is dropped and the message kept: an optional value or a vector or covariance with one becomes absent, a platform detail value becomes 0. The fields Sentinel owns (feed, replica, fencing token, observation id, raw payload) are ignored whatever the sender wrote. The Connections page shows each connection's endpoint, a test command and Go and Python senders; `GET /feeds/{id}` reports where it listens in `status.detail`: `listen{protocol,host,port}` (or `connect`), `format`, `tls`, `allowlist` (`open` or the entry count), `malformed` (messages the decoder rejected) and, for listeners, the sender table and counters described below. Its send guide also tests a TLS listener with `openssl s_client` (with `client.pem` and `client.key` when client certificates are required), shows a JSON sample for JSON connections, writes the Go and Python senders with TLS when the connection uses it, offers Copy on every snippet, and warns when a certificate is close to expiry (see Protection). Operators and admins also get a Recent rejects panel under it, which lists the connection's dead letters.

**Listeners.** A connection that binds a port (`tcp` in listen mode, `udp`, and `stream` with a `tcpserver` or `udp` transport) runs only on a *listener replica*: an ingest replica started with `INGEST_LISTENER=true` that uses the host's network, so any port chosen in Connections is reachable on the host with no port mapping. `INGEST_LISTENER_HOST` is the address senders use (`detail.listen.host`, shown in the send guide; the node address on Kubernetes unless `ingestListener.host` is set). Compose runs it as the `ingest-listener` service of the `inbound` profile (`docker compose --profile inbound up -d ingest-listener`, management API on `127.0.0.1:4010`); Docker Desktop on Mac and Windows needs Settings › Resources › Network › Enable host networking (4.34 and later), Linux needs nothing. The Helm chart runs it as `ingestListener` on a labelled node (`docs/infrastructure.md`). Placement among the live listener replicas follows the usual lease rules; `pinnedReplica` stays optional and, when set, overrides it. By default a listener replica runs listening connections only (a pin and `INGEST_LISTENER_SHARED`, below, are the exceptions); every other feed stays on the ordinary replicas, even during failover. While no listener replica is live, an enabled listening connection shows state `unassigned` with the last error `no listener replica (run the ingest listener: INGEST_LISTENER=true)`.

*Dedicated and shared.* A listener replica is dedicated by default, and there is no automatic failover onto it: when the only live replicas are listeners, every other enabled feed that is not pinned stays `unassigned` with the error `no ingest replica for this feed: the only live replicas are listeners, which run listening connections only (start ingest-service, or set INGEST_LISTENER_SHARED=true on the listener)` until an ordinary replica returns. While no ordinary replica is live, that row is readable only through the listener's own management API (`:4010`, with the service token), since the gateway talks to `ingest-service`. The listener is a single replica that does not scale out, and ordinary feeds piled onto it could take the listening connections down with them. A feed whose `pinnedReplica` names the listener still runs there. Setting `INGEST_LISTENER_SHARED=true` on the listener (valid only with `INGEST_LISTENER=true`; Helm `ingestListener.shared`) turns sharing and failover on: it then takes its rendezvous share of the ordinary feeds and steps in for them like any other replica, so give it the same credentials and settings as the ordinary replicas. With leases on (the default), every replica exports `sentinel_ingest_feeds_unplaced{reason}`, the number of enabled, unpinned feeds that no live replica may run (`no_listener` for listening connections, `no_ordinary_replica` for the others), and logs when it leaves or returns to zero, so the condition is visible even when the management API is not. Each replica counts the same feeds, so alert on `max()` across replicas, not `sum()`; under Helm the listener's own copy is scraped only with `ingestService.serviceMonitor.enabled` (its PodMonitor).

*Port rules.* The management API refuses (422, `details[{path,message}]` on `/config/port`, or `/config/transport/address` for `stream`) a listening port outside 1024-65535 (a policy floor so that the well-known ports stay with the host's own services; the listener image runs as the non-root user 10001, and the Helm chart also drops every capability, so the kernel would refuse them as well), a port another listening connection of the same protocol already uses (enabled or not, so enabling both later cannot clash; a TCP and a UDP connection may share a number) and a port Sentinel itself uses. Those are `INGEST_RESERVED_PORTS`, comma-separated ports and ranges, default `3000-3005,4000,4010,4200,5000,5001,5432,8080,8600,9000,9001,9092,9093,9200,9600`; an empty value means the default, and a value replaces it, so repeat what you still want. The replica that answers the request checks it, so set it the same on every ingest replica. A port already taken on the host by something else fails when the connection starts and appears as its last error.

*Protection.* `allow` lists the IPs and CIDRs that may send; an empty list is open to anyone who can reach the port. A sender that is not on it is dropped before any data is read (`rejected`). `maxConnections` caps concurrent TCP connections (`refused`); `maxMessagesPerSec` is shared by all senders of the connection, and what exceeds it is dropped (`rateLimited`); `maxMessagesPerSecPerSender` limits each sender IP address inside that (`senderRateLimited`); a TCP frame or UDP datagram over `maxMessageBytes` closes the TCP connection or drops the datagram (`oversize`). A `maxMessageBytes` or stream `maxFrameBytes` below 64 KiB now binds on the line, `xmlevent` and `beast` framings; their readers used to let up to 64 KiB through whatever was set, and the defaults are unchanged (tcp 65536, stream and TAK 1 MiB). A frame of exactly the limit passes and one byte more is `oversize` on every framing. A TCP connection may stay quiet indefinitely unless `readTimeoutSec` is set: then one that sends nothing for that many seconds is closed. A listener treats that as an ordinary disconnect; in connect mode it is recorded as the last error and Sentinel reconnects. With `tls.enabled` a TCP listener serves `tlsCert` and `tlsKey`; `tls.requireClientCert` makes it mutual TLS, accepting only clients whose certificate chains to `clientCa`; a `clientCa` secret without `requireClientCert` would verify nothing, so the connection refuses to start with it, and so it does with `requireClientCert` while TLS is off (`tcpserver: tls.requireClientCert is set but TLS is off; turn TLS on or remove requireClientCert`), which would otherwise leave a plain, open listener. Failed handshakes, and TLS clients on a plain listener, count as `tlsFailed`. In connect mode `serverCa` verifies the remote, `tlsCert` and `tlsKey` present a client certificate and `serverName` names the certificate to expect. `requireClientCert` is a listener setting, ignored by every dialer.

*Sender limits and the receive buffer.* `maxMessagesPerSecPerSender` (default 0, none) gives each sender IP address a limit of its own, whatever the number of its connections or source ports, inside the shared one; senders behind one NAT share a limit, and UDP source addresses can be forged. A burst of one second's worth is allowed, and the listener remembers up to 4096 senders' allowances, so a flood of forged addresses cannot grow it (a sender it forgot starts with a full allowance). Both limits count frames, which are a TCP line and a UDP datagram, so a JSON array counts once: a listener can take up to `maxMessagesPerSec` × 100 observations a second (100,000 at the default). `receiveBufferBytes` (UDP, default 4 MiB, at most 64 MiB) is the socket buffer the operating system keeps while Sentinel catches up; a burst beyond it is dropped by the kernel. The kernel grants at most `net.core.rmem_max` on the listener host (a Kubernetes listener shares its node's): raise it with `sysctl -w net.core.rmem_max=8388608`, persisted in `/etc/sysctl.d`, and the buffer you ask for is granted. `detail.receiveBufferEffectiveBytes` is what the kernel reports, which on Linux is twice the size it granted, so a stock host (212992) shows 425984 for the default. On Linux `kernelDropped` counts every datagram the kernel drops on the socket, from a full buffer, memory limits, checksum and filter drops alike.

*Certificates.* A TCP listener disables TLS session tickets, so every reconnect is a full handshake; with tickets, a TLS 1.3 sender that writes and closes at once would leave the server's ticket unread, the close would become a reset, and the last message would be lost. Every TLS transport but two reloads its certificate, key and CAs from their secret references and files every `INGEST_TLS_RELOAD_SEC` seconds (default 60, 0 turns it off), without dropping connections: new handshakes get the new material. The two that do not keep the TLS configuration they started with: an MQTT broker reached over `ws://` or `wss://` or through `all_proxy`, and the `tak` driver, which builds its TLS once. Restart those feeds to pick up new material. Files are read through the folder policy each time, so a Kubernetes Secret updated in place (the kubelet repoints `..data`) is followed; a variable cannot change under a running process, so rotate certificates as files. A reload that fails keeps the previous material, is logged and counted as `tlsReloadFailed`, and is tried again on the next tick; while it fails, `TLS reload failed: <err>; <previous error>` stands in front of the connection's last error (the previous error follows, so a handshake or dial error is not hidden). `detail.tlsReloads`, `detail.tlsReloadFailed` and `detail.tlsCertNotAfter` (RFC 3339) report it, and the gauge `sentinel_ingest_listener_tls_cert_expiry_timestamp_seconds` exports the expiry, so `sentinel_ingest_listener_tls_cert_expiry_timestamp_seconds - time() < 14 * 86400` alerts two weeks ahead. The send guide warns the same way: `TLS certificate expires on <date> (in N days)` with fewer than 14 days left, and `TLS certificate expired on <date>` after that.

*Senders and counters.* Per sender, `detail.senders[{remote,since,lastAt,messages,connected,rateLimited,malformed,lastReason,lastError,lastMalformedAt}]` lists the connected ones and those seen in the last 10 minutes (at most 50 listed), and `detail.distinctSenders` counts every sender the tracker holds (up to 1000 for UDP; up to 50 for TCP, more while more than 50 stay connected, because a connected sender is never evicted). A TCP row is a connection (`ip:port`); a UDP row is an IP address, whatever port its datagrams come from, while a UDP dead letter's `sender` and `sensorId` keep the `ip:port`. `lastAt` is left out until the sender has sent something. `rateLimited` counts messages dropped for going over the sender's own limit while the row was listed, so the listener's `senderRateLimited` can exceed the rows' sum. `malformed` counts the sender's messages that did not decode, and `lastReason`, `lastError` (cut to 200 bytes) and `lastMalformedAt` describe the last, left out until there is one. A sender, a row's `remote` or a `sensorId` that is text containing `://` (a websocket URL) is written without userinfo, query and fragment. The counters are `accepted`, `rejected`, `refused`, `rateLimited`, `senderRateLimited`, `oversize` and `tlsFailed`, and on a UDP listener `receiveBufferEffectiveBytes` and `kernelDropped` (always present; counted on Linux, 0 elsewhere); with certificate reload, `tlsReloads` and `tlsReloadFailed`.

*Error texts.* A decoder's error can repeat what a sender sent, so for a caller whose clearance is below the feed's classification the API empties `status.lastError` when it is the decoder's text and removes `detail.lastDecodeError` and each `detail.senders[].lastError`; the driver-specific ones, `detail.errors.<selection>` of `celestrak` and `detail.lastError` of `httpjson`, keep their keys with the texts blanked. Counts, times and reason codes remain. A status row written by an older replica lacks `lastDecodeError` for the non-stream drivers, so its decode text is not blanked until the owning replica runs the new version.

*Security notes.* UDP source addresses can be forged, so a UDP allowlist stops mistakes, not attackers: on a network you do not trust use TCP with mutual TLS and an allowlist. An empty allowlist is open. The listener replica's own management API is guarded only by `INGEST_SERVICE_TOKEN` (`/health` and `/metrics` there are open). Compose binds it to `127.0.0.1:4010`, so it is not reachable from the network; the Helm chart binds `:4010` on every interface of the node for the kubelet probes, so keep `:4010` closed to outside networks there. Change the default `dev-ingest-token` anywhere but a development machine.

Decoders for `stream` (`tcp` and `udp` pick one with `format`):

| Decoder | Input | Source | Notes |
|---------|-------|--------|-------|
| `sentinel` | `sentinel.v1.Observation`, binary protobuf or JSON (`tcp` and `udp` only, `format: sentinel`) | from the message (`defaultSource`) | Server-owned fields ignored; `missing_identity` and `bad_position` dead-lettered. A JSON line may be an array of up to 100 observations (`batch_too_large` past that), refused whole when an element is bad |
| `json` | JSON object or array, or a batch document with `records` | `options.source` (UNSPECIFIED) | Field map (`fields.latitude`, `fields.longitude` required; id, name, altitude, speed, heading, course, timestamp, callsign, …), `identityType`, `timeFormat`, `altitudeUnit`, `speedUnit`, `entityType`. The default map is the legacy position shape |
| `sbs` | BaseStation CSV (readsb port 30003) | ADS_B | MSG 2/3 fixes; MSG 1/4/5/6/8 as positionless partial observations |
| `beast` | Mode-S Beast binary (readsb port 30005, `framing: beast`) | ADS_B | Identification, CPR airborne position (global pair within 10 s, then local), velocity, status, Mode S altitude and squawk replies for known aircraft |
| `nmea-ais` | NMEA VDM/VDO (AIS-catcher, receivers) | AIS | Types 1–3, 5, 18, 19, 21, 24, 27; fragments reassembled per sender. A frame that carries nothing (a heartbeat, a partial fragment, an unsupported message) is counted as skipped by reason; a frame that fails to decode is dead-lettered; a decoder panic is recovered and dead-lettered.

Backpressure between a transport and its decoder: `tcpclient`, `tcpserver` and `websocket` block (TCP flow control reaches the sender), `udp` drops, `stomp` nacks, `mqtt` blocks up to 2 s then drops. All of it is counted (`sentinel_ingest_frames_dropped_total`, `sentinel_ingest_nacked_total`, `sentinel_ingest_blocked_seconds_total`).

Recipes for readsb, AIS-catcher, a TAK server, a JSON API and external systems sending over TCP or UDP are in `docs/development.md`.

## Replicas and operations

- Environment: `KAFKA_BROKERS`, `KAFKA_OBSERVATION_TOPIC`, `KAFKA_DEADLETTER_TOPIC`, `DATABASE_URL`, `HTTP_ADDR`, `INGEST_SERVICE_TOKEN` (required in production), `INGEST_LISTENER` (`true` makes the replica a listener: it takes listening connections and runs nothing else, unless a feed is pinned to it), `INGEST_LISTENER_SHARED` (`true`, only valid with `INGEST_LISTENER=true`, lets the listener run ordinary feeds too; default `false`), `INGEST_LISTENER_HOST` (the address senders use), `INGEST_RESERVED_PORTS` (ports a listening connection may not take; blank is the default list), `INGEST_SECRET_ENV_ALLOW` and `INGEST_SECRET_FILE_DIRS` (what a secret reference may name; see Configuration and secrets), `INGEST_TLS_RELOAD_SEC` (how often TLS certificates are reloaded, default 60, 0 off), `REPLICA_ID` (hostname; the pod name in Kubernetes, except the Helm listener's, which is its Deployment name so that a pin to it survives a rollout), `FEEDS_BOOTSTRAP_ENABLED` (built-ins inserted enabled on first start), `PUBLISHER_SHARDS`, `OBS_BUFFER`, `FRAME_BUFFER`, `RAW_PAYLOAD_MAX_BYTES`, `DLQ_RATE_PER_SEC`, `DLQ_PEEK_MAX_SCAN` (messages of each dead-letter partition read to find a connection's recent dead letters, default 2000; 0 turns viewing off and the endpoint answers 501; negative is refused at start), `FEED_STALE_*`, `FEED_RETRY_*`, `LEASE_ENABLED`, `LEASE_TTL_SEC`, `LEASE_TICK_SEC`, `LEASE_REBALANCE_SEC`, `SHUTDOWN_TIMEOUT_SEC`. The service refuses to start, with the variable named, on a setting it cannot read: an integer setting that is not an integer, and a boolean one (`INGEST_LISTENER`, `INGEST_LISTENER_SHARED`, `LEASE_ENABLED`) that is not what Go's `strconv.ParseBool` reads (`1`, `t`, `true`, `0`, `f`, `false`, in the usual cases; `ture` or `yes` is refused rather than read as the default). A listener needs leases: `INGEST_LISTENER=true` or `INGEST_LISTENER_SHARED=true` together with `LEASE_ENABLED=false` is refused, since without leases it would run every feed. A listener with an empty `INGEST_LISTENER_HOST` starts with a warning, because the send guide would show senders a blank address.
- Scaling: `docker compose up -d --scale ingest-service=3`; the Helm chart's `ingestService.replicaCount`. Site receivers should be pulled (`tcpclient`, or `tcp` in connect mode) rather than listened for, so any replica can own them; connections that listen run on the listener replica, which does not scale out and runs nothing else (unless a feed is pinned to it or `INGEST_LISTENER_SHARED=true`).
- Shutdown: readiness turns 503, the supervisor stops every driver and writes stopped status rows, the publisher drains, the producer flushes, leases and the replica row are released, bounded by `SHUTDOWN_TIMEOUT_SEC`.
- Startup and upgrades: at start, before it bootstraps the built-in feeds or runs a feed, the service checks that the database has the columns it needs, and exits with the fatal log `database schema is out of date` when it does not. The error names the missing columns and the file that adds them, for example `database schema is older than this ingest-service: missing sentinel.ingest_replicas.listener (db/schema/70_feeds.sql). Apply db/schema in name order, every file is idempotent: ...` followed by the Compose, Helm and psql commands. When the check itself fails (the database is unreachable, say), the fatal log is `checking the database schema failed` instead, and applying the schema will not help. Apply `db/schema` before starting a new version; every file is idempotent (`docs/development.md` has the Compose, Make and psql commands; under Helm the `dbSchema` Job applies it, see `docs/infrastructure.md`). Upgrade `ingest-service` before, or together with, `ingest-listener`: a new dedicated listener beside an old `ingest-service` leaves ordinary feeds flapping (about 30 s on, 15 s off).
- Metrics (`/metrics`), each named `sentinel_ingest_<name>` (for example `sentinel_ingest_leases_lost_total`): `observations_received_total` (observations drivers emitted, not frames: a JSON array line is one frame and up to 100 observations), `observations_total`, `decode_errors_total`, `skipped_total`, `frames_dropped_total`, `nacked_total`, `blocked_seconds_total`, `duplicates_total`, `feeds_running`, `feed_last_success_timestamp`, `feed_entities_count`, `feed_errors_total`, `feed_restarts_total`, `leases_lost_total`, `lease_handovers_total`, `feeds_unplaced`, `observations_published_total`, `observations_delivery_failed_total`, `deadletter_total`, `deadletter_dropped_total` (also by `reason`: `rate_limited`, `closing` while the service shuts down, `produce_failed`), `publisher_shard_depth`, `publisher_blocked_seconds_total`, for connections that send, `outbound_events_total`, `outbound_denied_total`, `outbound_dropped_total`, `outbound_delivery_errors_total` and `outbound_lag_seconds`, and for listening connections `listener_events_total{feed_id,driver,event}` (`event` is `accepted` for frames taken in, which is the frame count, then `rejected`, `refused`, `rate_limited`, `sender_rate_limited`, `oversize`, `tls_failed`, `tls_reload_failed`, and `kernel_dropped` for a datagram listener, which counts only on Linux and stays 0 elsewhere), `listener_connections{feed_id,driver}` (TCP only), `listener_senders{feed_id,driver}` and, for a connection that serves TLS, `listener_tls_cert_expiry_timestamp_seconds{feed_id,driver}`. The sender is never a label. The listener series exist only on the replica that runs the feed and start again from zero when the feed restarts (`rate()` copes); a UDP listener exports `refused` and `tls_failed` at 0 (and `kernel_dropped` at 0 off Linux), and `listener_senders` stops at the tracker's cap. The other series are labelled by `feed_id` (with `driver`, `reason` or `kind` where they apply), except `feeds_running` (per `driver`), `publisher_shard_depth` (per `shard`), `feeds_unplaced` (per `reason`) and `publisher_blocked_seconds_total` (no labels). `leases_lost_total` counts the feeds this replica stopped because another replica took their lease, `lease_handovers_total` the feeds it handed to their preferred replica; `feeds_unplaced` is described under Listeners.
- Kafka: `observations.raw` (24 partitions, 3 days, key = `ICAO24:ABC123` or `feed:<id>:<sourceEntityId>`), `observations.dlq` (3, 30 days). Headers on every observation: `content-type`, `schema`, `schema-version`, `producer`, `feed-id`, and `x-fence` when the replica holds a fencing token (leases on). A dead letter carries exactly `producer`, `feed-id`, `driver`, `decoder`, `sender`, `reason`, `error` and `received-at`, and, when its payload was over 64 KiB, `raw-truncated` (`true`) and `raw-size` (the payload's original size in bytes). The value is cut to 64 KiB because a stream frame can be 1 MiB, which is over the producer's message limit and would be refused whole. A dead letter the producer refuses anyway (its queue is full, say) is logged and counted in `deadletter_dropped_total`. `decoder` is empty when the source has none (a polled response), `sender` is the remote address, topic or queue (empty when the driver does not know it; text containing `://` is stored without userinfo, query and fragment), and `received-at` is when the frame arrived (RFC 3339), not when it was dead-lettered. The topic keeps them 30 days, so a sender's IP address stays in a header that long.
- Dead-letter viewing: `GET /feeds/{id}/deadletters` reads the last `DLQ_PEEK_MAX_SCAN` messages of each partition of `observations.dlq` without a consumer group, so it commits nothing and no service sees it, and returns the feed's newest within 5 s (`partial: true` when the read stopped at that limit; `scanned` counts every feed's messages it read). `at` is the `received-at` header, or Kafka's own time when that is missing. `size` is the payload's original size (the `raw-size` header when the publisher cut it), and `payloadTruncated` is true whenever the payload shown is less than that. The Connections page shows the same list under Recent rejects, with the payload on request. `celestrak` dead-letters a response it cannot parse as `parse_error`, up to 64 KiB. A topic that is missing, or a broker or permission that fails, is a 502 and a warning in the ingest log.

## Adding a driver

Everything lives under `apps/ingest-service/internal/source`.

1. **Decide the shape.** A new wire format over an existing transport is a decoder; a new way to fetch (an API with its own scheduling or request shaping) is a driver; a new way to move bytes is a transport.
2. **Decoder** (`decoder/<name>/`): implement `decoder.Decoder` (`Decode(transport.Frame) ([]*obs.Observation, error)`, `Close()`), fill the object fields of `obs.Observation` (source entity id, `Source`, entity type, environment, position with `SetPosition`, kinematics with `obs.Float`, identities with `AddIdentity`, a platform block), return `decoder.Skip(reason)` for frames that carry nothing and an error for frames that are broken. Register in `init()` with `decoder.Register(decoder.Definition{Name, Description, Source, ContentType, New})`, add the name to the `decoder.name` enum in `driver/stream/schema.json`, and write table tests on real frames.
3. **Driver** (`driver/<name>/`): embed a `schema.json`, implement `driver.Driver` (`Run(ctx, sink)`, `Health()`), use `httppoll.NewScheduler` and `httppoll.NewClient` for a poller, implement `aoi.AreaAware` when the area of interest shapes requests, and register in `init()` with `driver.Register(driver.Definition{ID, Name, Description, Source, Capabilities, SecretFields, AreaTTL, ConfigSchema, New})`. Emit through the sink (`Emit`, `Succeeded(count)`, `Skipped(reason)`, `DeadLetter`); never touch Kafka or the generated protobuf code.
4. **Transport** (`transport/<kind>/`): implement `transport.Transport` (`Run(ctx, emit)`, `State()`), honour `ErrBackpressure` from the emit, and register with `transport.Register`.
4b. **Sink or bidirectional driver** (a connection that sends): set `Direction: driver.DirectionOut` (or `DirectionBoth` when it also receives) in the definition and implement `driver.Consumer` beside `driver.Driver`: `HandleEntity(ctx, driver.EntityUpdate)` gets an upsert with the full `sentinel.v1.Entity` snapshot or a removal (`Reason` `deleted`, `aged_out` or `policy`), `HandleAlert(ctx, *sentinelv1.AlertEvent)` gets triggered, acknowledged and resolved alerts. Calls arrive from one goroutine per connection, already filtered by the policy, coalesced and rate-limited; return `driver.ErrNotConnected` while the remote is unreachable so the pump pauses and keeps its queue, any other error counts a delivery failure. `Run` owns the session (and the inbound side for `both`); the supervisor runs the pump beside it and restarts the connection when either stops. Read Sentinel's own geofences and locations through `deps.Shapes` when the remote can show them. The `tak` driver and the `cot` encoder are the reference.
5. **Register the package** with one import line in `source/all/all.go`, add a validation case to `drivers/catalog_test.go`, and a recipe to `docs/development.md`.
6. **Try it live**: create the feed through `POST /api/v1/feeds`, watch `GET /api/v1/feeds/{id}/status` and `/metrics`, and confirm observations on `observations.raw` and nothing unexpected on `observations.dlq`.
